# 每周阅读导读

用户每周收藏几十篇文章，读不完。这个流程替用户先读一遍：说清每篇讲了什么、值不值得读、读哪几段，并在用户的反馈里逐步校准推荐。

程序在项目 `~/Documents/Projects/knowledge-distill`（Python 用项目里的 `.venv/bin/python`）：

| 脚本 | 作用 |
|---|---|
| `tools/cubox_pull.py` | 拉 Cubox 入库，末尾自动跑微信读书同步（划线、想法回到库里） |
| `tools/weekly_digest.py` | `dump` 导出文章文本；`add` 存摘要（引文逐字核对）；`plan` 存分档；`render` 写库里的导读笔记 |
| `tools/weekly_epub.py` | 打包 EPUB 到 `~/Downloads/2026Wxx资料汇总.epub` |
| `tools/weread_sync.py` | 微信读书里的划线和想法回到文章笔记；对导读章、摘要卡的回到导读笔记 |

库：`~/Documents/Obsidian/simon1561`。导读笔记在 `01_学习和思考/00_Capture/导读/2026Wxx 导读.md`，偏好档案在 `04_参考资料/个人项目/个人笔记系统/阅读偏好档案.md`。数据在项目 `data/digest/`（不进 git）。

## 硬规则

- **自己读、自己判断**。不把阅读、摘要、分类、推荐交给 opencodex 上的其他模型，除非用户当次明确指定。
- **每次先读偏好档案**，推荐以档案为准；本 skill 不重复档案里的标准。档案里〔推断〕的条目只作参考，〔确认〕的必须遵守（例如默认精读的作者、每周精读上限）。
- 摘要转述作者观点，推荐是 AI 的判断，两者分开写，都不写成用户的看法。
- 引文必须逐字出自原文，`add` 会核对；对不上的会被拒，改了重来。
- 档案只出修改提案，用户确认后才改，并在档案「修改记录」写一行。
- 删除文件一律移到废纸篓。改完程序测试通过后在项目里 git commit（不 push）。

## 流程

### 1. 先收上周的反馈

拉过 Cubox（或单独跑 `tools/weread_sync.py`）之后：

- 读上周的导读笔记，找 `<!--co:` 开头的批注（用户在微信读书里对导读或摘要卡写的想法）和 `==…==` 划线。
- 查上周那批文章笔记里新增的划线和想法（同上两种标记）。
- 有反馈时，先就推荐逻辑问用户：例如某篇推荐浏览、但用户划了很多，问是推荐低估了，还是只是个别段落有用。按回答拟档案修改提案。
- 导读末尾的两个问题（本周取舍、哪些文章有价值）用户回答了的，同样整理成提案。

### 2. 导出并通读

```bash
.venv/bin/python tools/weekly_digest.py dump --week 2026-Wxx
```

文本在 `data/digest/texts/<week>/NNN.txt`，`index.tsv` 是编号、字数、文件名。每篇都要读完再写，不凭标题和开头判断。长文可以先看小标题和段落开头定位，但关键数据、限定语要回原文确认。

### 3. 写摘要（分批 `add`）

每批写一个 JSON（放 `data/digest/work/bNN.json`），格式见 `references/formats.md`。要点：

- `gist` 一两句说清作者的主要结论；`points` 3～4 条，含关键数字。
- **证据身份写清**：创始人称、公司内部数据、作者测算、模型估算、在某假设下；未点名的公司写「文中未点名，据……疑指……」，不写「显然」。
- `source`：原始发布 / 完整译文 / 节选整理 / 二手评论。
- `substance` 一句话评价信息含量和局限；`category` 是 EPUB 无导读时的分组。
- 已有条目可以只给要改的字段。

```bash
.venv/bin/python tools/weekly_digest.py add data/digest/work/bNN.json --week 2026-Wxx
```

### 4. 分档（`plan`）

先把相关文章归成话题组，判断同一组是不是在回答同一个问题，再分档。按档案的标准；写法要求：

- **推荐理由**：解决什么问题、有什么别处没有的信息、为什么值得这个阅读时间。不写「和你的主线直接相关」这类空话。
- **精读**：最多 10 篇（档案为准），档案里默认精读的作者必须进。每篇给 `action`（读哪几段）和 `focus`（重点段落的起止句，逐字取自原文，书里会加底色）。起止句取段落开头十几个字即可，`plan` 会核对能否找到。
- **浏览**：`action` 写「读摘要即可」「看指定段落：……」或「有具体问题再查全文」；看指定段落的也可以给 `focus`。
- **可跳过**：`action` 写「信息重复」或「当前低优先级」。
- **多个版本**：组里定一个 `version: 主版本`，其他标「有补充」「无新增」「有纠错」；只有无新增的放可跳过。
- **来源疑点**：放 `flags`（如「创始人自述数据，未经核实」「整理稿拼接了历史演讲」），任何一档都可以有。
- **邻近探索**（`outside`）：0～2 篇，关注范围边上、体裁或视角不同的好文章；没有就不选。
- **`overview`**：三四段，说本周按什么挑的、同主题怎么去重、边界上的取舍。
- **`question`**：本周最拿不准的一个取舍，问成具体的二选一。

```bash
.venv/bin/python tools/weekly_digest.py plan data/digest/work/plan.json --week 2026-Wxx
.venv/bin/python tools/weekly_digest.py render --week 2026-Wxx
```

导读笔记里已有用户的划线或批注时，`render` 会拒绝覆盖；这时先把反馈收完，再和用户商量。

### 5. 检查并出书

- 用 report-writer 的 `deliver.py <导读笔记> --target obsidian` 检查格式，读完整输出。
- 抽读导读：推荐逻辑是否和分档一致，理由是否具体，是否有把作者观点写成事实的地方。

```bash
.venv/bin/python tools/weekly_epub.py --week 2026-Wxx
```

EPUB 结构：导读章 → 精读 → 邻近探索 → 浏览 → 可跳过；每篇开头一张 AI 摘要卡，重点段落有底色；图片已压缩（最宽 1200 像素）。

### 6. 交付

告诉用户：精读几篇、各是什么，本周导读末尾的问题，EPUB 位置和大小，需要用户确认的档案提案。更新项目的 `docs/采集待办.md`；有流程变化时在库里的「个人笔记系统 工作记录」追加一条。
